\section{Introduction}
Ce document décrit le système d'annotations Java conçu pour la génération automatique de diagrammes PlantUML. L'outil gère nativement les concepts standards --- héritage via \texttt{extends}, implémentation via \texttt{implements}, classes abstraites, énumérations, \textit{records} ; les annotations ci-dessous viennent enrichir et paramétrer cette analyse. Seul le \textbf{diagramme de classes} est visé. Le lecteur pressé peut commencer par le mode d'emploi (section \ref{sec:modedemploi}).

\subsection{Comment le code est lu}
\label{sec:lecture}

La bibliothèque travaille \textbf{par réflexion sur les classes compilées} : on lui désigne un répertoire de \texttt{.class} (typiquement \texttt{target/classes}), et non un répertoire de sources. \textbf{Ce que la compilation efface est perdu pour le générateur} : les valeurs d'initialisation des attributs et le corps des méthodes --- d'où une dépendance qui ne se lit que dans un appel devra être déclarée. Les \textbf{signatures déclarées}, elles, survivent à l'effacement de type : un \texttt{List<Commande>} dit à lui seul quelle classe l'association vise. Les \textbf{noms des paramètres de méthode}, enfin, ne sont écrits dans les \texttt{.class} que si le projet est compilé avec \texttt{-parameters} (section \ref{sec:membres}).

Une seconde lecture, indépendante, a lieu \textbf{à la compilation} : la bibliothèque embarque un processeur d'annotations qui vérifie ce que le développeur écrit, là où il l'écrit (section \ref{sec:verification}).

\subsection{Les trois endroits où quelque chose se décide}
\begin{itemize}
    \item une \textbf{annotation} dit une chose sur \textit{cet} élément-ci ;
    \item le fichier \textbf{\texttt{umlg.json}} dit une chose qui vaut pour tout le projet, ou pour une vue (section \ref{sec:regles-projet}) ;
    \item l'\textbf{appel du générateur} dit ce qui ne touche pas au modèle --- l'apparence, la destination (sections \ref{sec:style} et \ref{sec:sortie}).
\end{itemize}
Le partage est étanche : aucune règle ne refait ce qu'une annotation sait faire, et réciproquement (section \ref{sec:partage}). Dans le cas nominal, \texttt{@UMLClass} suffit.

\section{Règles générales et conventions}
\label{sec:regles}

\subsection{Convention de nommage}
Tout paramètre désignant une classe visée par un lien s'appelle \texttt{target} (et \texttt{source} pour l'extrémité de départ), uniformément sur \texttt{@UMLAssociation}, \texttt{@UMLAssociationClass} et \texttt{@UMLDependency}.

\subsection{Comment un membre est écrit}
\label{sec:membres}

Le générateur emploie la notation d'UML, \textbf{\texttt{nom : Type}}, les deux-points entourés d'espaces.

\begin{lstlisting}
class "Vol" {
  - departureTime : Date
  - escales : Aeroport [0..*]
  --
  + reporter(nouvelleHeure : String, minutes : int) : void
  + {static} /compter(code : String) : int
}
\end{lstlisting}

L'ordre des morceaux est fixe. Pour un attribut : la visibilité, \texttt{\{static\}} s'il y a lieu, le nom (précédé de sa barre oblique s'il est dérivé), le type, la multiplicité entre crochets, puis les contraintes entre accolades. Pour une méthode : la visibilité, \texttt{\{static\}}, le nom, les paramètres entre parenthèses, le type de retour, puis sa multiplicité.

\begin{itemize}
    \item \textbf{Le type de retour} est écrit par défaut, \texttt{void} compris ; la règle \texttt{"omit": ["return void"]} l'efface pour tout le projet.
    \item \textbf{Les noms des paramètres} ne sont affichés que si le projet a été compilé avec \texttt{-parameters} (section \ref{sec:modedemploi}) ; sinon la signature se réduit à \texttt{reporter(String, int) : void}. Un avertissement le \textbf{signale} quand aucun paramètre d'aucune méthode dessinée ne porte de nom.
    \item \textbf{L'ordre des membres} est \textbf{alphabétique} par défaut, la réflexion ne promettant aucun ordre stable ; \texttt{"order": "declaration"} rétablit l'ordre du source. Les littéraux d'une énumération font exception : leur ordre est celui des ordinaux.
    \item \textbf{Devant une multiplicité}, le type écrit est celui de l'\textbf{élément}, jamais celui du conteneur : un \texttt{Set<String>} marqué \texttt{[0..*]} s'écrit \texttt{alias : String [0..*]}. Une \texttt{Map}, ayant deux paramètres, s'écrit en entier.
    \item \textbf{La multiplicité} n'est écrite que déclarée : par \texttt{targetMultiplicity} sous \texttt{notation = ATTRIBUTE} (section \ref{sec:notation}), ou par \texttt{@UMLMultiplicity} (section \ref{sec:multiplicite}). Absente, elle vaut \textit{exactement un}.
\end{itemize}

\subsection{Directions et répétabilité}
\texttt{UMLDirection} (\texttt{NONE}, \texttt{UP}, \texttt{DOWN}, \texttt{LEFT}, \texttt{RIGHT}) est utilisé partout où une orientation est demandée ; \texttt{NONE} est le défaut, PlantUML plaçant alors l'élément lui-même.

\texttt{@UMLDependency}, \texttt{@UMLNote} et \texttt{@UMLConstraint} sont \texttt{@Repeatable}. Les autres (\texttt{@UMLClass}, \texttt{@UMLAssociation}, \texttt{@UMLAssociationClass}, \texttt{@UMLMultiplicity}, \texttt{@UMLPackage}, \texttt{@UMLDerived}, \texttt{@UMLInclude}, \texttt{@UMLExclude}) sont uniques sur leur cible.

\begin{lstlisting}
@UMLDependency(target = ServiceBancaire.class, label = "facture via")
@UMLDependency(target = Journal.class, label = "trace")
@UMLClass
public class Panier { }
\end{lstlisting}

\subsection{Cibles autorisées}
\begin{center}
\begin{tabular}{@{}L{3.8cm}L{12.8cm}@{}}
\hline
\textbf{Cible} & \textbf{Annotations acceptées} \\
\hline
Type \newline \small(classe, interface, énumération) &
\texttt{@UMLClass}, \texttt{@UMLPackage}, \texttt{@UMLAssociationClass}, \texttt{@UMLDependency}, \texttt{@UMLNote}, \texttt{@UMLConstraint} \\[0.4em]
Attribut &
\texttt{@UMLInclude}, \texttt{@UMLExclude}, \texttt{@UMLAssociation}, \texttt{@UMLMultiplicity}, \texttt{@UMLDerived}, \texttt{@UMLConstraint}, \texttt{@UMLNote} \\[0.4em]
Méthode &
\texttt{@UMLInclude}, \texttt{@UMLExclude}, \texttt{@UMLMultiplicity}, \texttt{@UMLDerived}, \texttt{@UMLNote} \\
\hline
\end{tabular}
\end{center}
Une annotation posée hors de ces cibles est rejetée à la compilation.

\subsection{Quand deux annotations se rencontrent}
Le détail est réuni en section \ref{sec:verification}. Trois arbitrages valent d'être connus d'emblée : une \textbf{classe visée par un lien sans \texttt{@UMLClass}} est une erreur, tandis que les héritages sont ignorés silencieusement --- aucune classe n'est créée implicitement ; sur un attribut porteur d'une \texttt{@UMLAssociation}, les annotations \texttt{@UMLConstraint}, \texttt{@UMLDerived} et \texttt{@UMLExclude} s'appliquent à l'\textbf{association}, c'est-à-dire au trait ou à la ligne ; et une association est \textbf{toujours} dessinée, quelle que soit la stratégie de visibilité.

\section{Le Déclencheur et le Seuil : \texttt{@UMLClass}}

Placée sur une classe, interface ou énumération, elle indique que l'entité doit figurer sur le diagramme et fixe un seuil de visibilité par défaut pour ses membres. Elle choisit le périmètre : sans elle, rien n'est dessiné.

\begin{itemize}
    \item \texttt{name} (String) : surcharge le nom affiché.
    \item \texttt{color} (String) : couleur de fond --- code hexadécimal (\texttt{"\#DDEEFF"}, \texttt{"\#ABC"}, \texttt{"\#FF000080"} avec transparence) ou nom PlantUML (\texttt{"LightBlue"}), vérifié contre le catalogue du moteur qu'énumère \texttt{UMLGenerator.knownColors()}.
    \item \texttt{stereotype} (String) : étiquette métier (ex. \texttt{"Service"}). Les guillemets \texttt{<<~>>} sont posés par le générateur.
    \item \texttt{strategy} (Enum) : le seuil de visibilité. \textbf{\texttt{PROJECT}}, le défaut, s'en remet à la clé \texttt{strategy} du fichier \texttt{umlg.json}, ou à \texttt{NONE} si le projet n'en déclare aucune ; \textbf{\texttt{NONE}} donne une coquille vide, sauf les membres explicitement \texttt{@UMLInclude} ; \textbf{\texttt{PUBLIC}}, \textbf{\texttt{PROTECTED}}, \textbf{\texttt{PACKAGE}} et \textbf{\texttt{PRIVATE}} retiennent respectivement les membres \texttt{public} ; \texttt{public} et \texttt{protected} ; \texttt{public} et sans modificateur ; tous.
\end{itemize}

\paragraph{Les composants d'un record échappent à la stratégie} et se dessinent même sous \texttt{NONE}. \texttt{@UMLExclude} garde le dernier mot ; un champ \textit{ajouté} au record (forcément statique) reste un membre ordinaire.

\paragraph{Rien n'est masqué sans demande.}
\label{sec:bruit}
Le tri se déclare dans \texttt{umlg.json} (section \ref{sec:regles-projet}). Seul est écarté d'office ce que le compilateur a fabriqué --- attributs synthétiques, référence à la classe englobante. Les constructeurs ne sont jamais lus, et aucune annotation ne peut en faire apparaître un.

Ci-dessous, le projet a écrit \texttt{"hide": ["get*"]} dans son \texttt{umlg.json} ; sans cette entrée, \texttt{getPseudo()} paraîtrait comme n'importe quelle autre méthode publique.
\begin{lstlisting}
// Affiche les membres que la strategie autorise, moins ce que le
// fichier de regles ecarte.
@UMLClass(stereotype = "Entity", strategy = UMLVisibility.PACKAGE)
public class Utilisateur {
    public String pseudo;       // Sera affiche
    String email;               // Sera affiche (package-private)
    protected int age;          // Sera ignore (hors strategie)
    private String motDePasse;  // Sera ignore (hors strategie)

    public Utilisateur() {}     // Sera ignore (jamais de constructeur)
    public String getPseudo() {}// Sera ignore (motif "get*" de hide)

    public void valider() {}    // Sera affiche (methode metier publique)
}
\end{lstlisting}

% ---------------------------------------------------------
\section{La Dérogation d'Exclusion : \texttt{@UMLExclude}}

Force la dissimulation d'un attribut ou d'une méthode que la \texttt{strategy} autorisait à paraître --- loggers, constantes internes. \textbf{Aucun paramètre.}

Posée sur la déclaration d'une méthode --- dans une interface, ou dans une classe parente ---, elle vaut pour \textbf{chacune de ses redéfinitions}. Une méthode statique ou privée, qui ne redéfinit rien, ne regarde qu'elle-même.

\begin{lstlisting}
@UMLClass(strategy = UMLVisibility.PRIVATE)
public class ConnexionBase {
    private String url; // Affiche car strategie globale sur PRIVATE

    @UMLExclude
    private Logger log; // Ignore explicitement pour alleger le graphe
}
\end{lstlisting}

\section{La Dérogation d'Inclusion : \texttt{@UMLInclude}}

Force l'apparition d'un membre que son niveau d'encapsulation aurait masqué, et peut de surcroît le \textbf{renommer}.
\begin{itemize}
    \item \texttt{name} (String) : le nom sous lequel le membre paraît, à la place du sien. La chaîne vide, le défaut, veut dire « le nom du code ». Les notes suivent le nom affiché.
    \item \texttt{asAttribute} (boolean, \texttt{false} par défaut) : écrit la méthode en \textbf{notation attribut} --- \texttt{xKeycodeByXKeyName : Map<String, Short>}, sans parenthèses, dans le compartiment des attributs. Exige une méthode \textbf{sans paramètre} qui \textbf{rend quelque chose} ; la ligne garde son soulignement si la méthode est statique, sa barre oblique si elle est dérivée, sa multiplicité si elle en porte une.
\end{itemize}

\paragraph{Sur un composant de record, une seule ligne.} Le compilateur recopie l'annotation sur le champ \textbf{et} sur l'accesseur ; seul le composant est retenu. Une \texttt{@UMLInclude} posée sur un accesseur \textit{écrit à la main} reste, elle, affichée.

\begin{lstlisting}
@UMLClass(strategy = UMLVisibility.PUBLIC)
public class MoteurDeRecherche {

    public void chercher() {} // Affiche car public

    private int compteur; // Ignore car private

    @UMLInclude
    private void algorithmeSecret() {} // Force l'affichage grace a l'annotation

    @UMLInclude(name = "xKeycodeByXKeyName")
    public Map<String, Short> codeByName() { ... }
    // Affiche : xKeycodeByXKeyName() : Map<String, Short>
}
\end{lstlisting}

\section{La Précision Métier : \texttt{@UMLAssociation}}

Précise la sémantique UML d'une relation portée par un attribut : type de lien, multiplicités, rôles, classe ciblée. Le code \texttt{List<Commande> commandes} indique qu'il y a plusieurs commandes ; seul le métier sait si c'est \texttt{0..*} ou \texttt{1..*}, et s'il s'agit d'une association ou d'une composition.

\begin{itemize}
    \item \texttt{target} (Class) : la classe cible. \textbf{Facultatif}, le type de l'attribut la nommant déjà (section \ref{sec:lecture}) ; nécessaire quand le type ne dit rien --- collection sans paramètre, \texttt{Map} dont on ne saurait quelle moitié est visée, classe absente du type.
    \item \texttt{notation} (Enum) : \texttt{ARROW} (défaut) ou \texttt{ATTRIBUTE} --- la \textbf{forme} du dessin (section \ref{sec:notation}).
    \item \texttt{type} (Enum) : \texttt{ASSOCIATION}, \texttt{COMPOSITION}, \texttt{AGGREGATION}.
    \item \texttt{sourceMultiplicity}, \texttt{targetMultiplicity} (String) : multiplicités (ex. \texttt{"1"}, \texttt{"0..1"}, \texttt{"0..*"}) ; \texttt{sourceRole}, \texttt{targetRole} (String) : noms des rôles aux extrémités ; \texttt{label} (String) : texte sur la flèche ; \texttt{direction} (Enum) : \texttt{UMLDirection}, qui contraint le placement de \textit{ce} trait.
\end{itemize}

\noindent L'ordre n'est pas un paramètre : il s'écrit \texttt{@UMLConstraint(rule = "ordered")}, comme n'importe quelle autre règle formelle.

\begin{lstlisting}
@UMLConstraint(rule = "ordered")
@UMLAssociation(target = Commande.class, targetMultiplicity = "0..*")
private List<Commande> commandes;   // "achats 0..* {ordered}"
\end{lstlisting}

\begin{lstlisting}
public class Utilisateur {
    @UMLConstraint(rule = "ordered")
    @UMLAssociation(
        target = Commande.class,
        type = UMLRelationType.COMPOSITION,
        sourceMultiplicity = "1",
        targetMultiplicity = "0..*",
        targetRole = "achats",
        label = "passe"
    )
    private List<Commande> commandes;
}
\end{lstlisting}

\subsection{Les deux notations d'une association}
\label{sec:notation}

UML n'autorise \textbf{qu'une notation à la fois} : un trait entre deux boîtes, ou une ligne dans la boîte de départ. Sous \texttt{ARROW} l'attribut est retiré de la boîte au profit du trait ; sous \texttt{ATTRIBUTE} il y reste et aucun trait n'est tracé.

\begin{center}
\begin{tabular}{@{}L{2.9cm}L{6.0cm}L{7.6cm}@{}}
\hline
\textbf{Valeur} & \textbf{Ce qui est dessiné} & \textbf{Quand la choisir} \\
\hline
\texttt{ARROW} \newline \small(défaut) & Un trait décoré à ses extrémités : \newline \texttt{Client "1" *-{}- "achats 0..*" Commande} & Les associations qui structurent le domaine, celles que le lecteur doit voir en premier. \\[0.4em]
\texttt{ATTRIBUTE} & Une ligne du compartiment des attributs : \newline \texttt{- commandes: Commande [0..*]} & Quand une classe en cite dix autres, ou quand la cible n'a rien d'intéressant à montrer. \\
\hline
\end{tabular}
\end{center}

\begin{lstlisting}
@UMLClass
public class Client {
    // Un trait vers Commande (comportement par defaut).
    @UMLAssociation(target = Commande.class, targetMultiplicity = "1")
    private Commande courante;

    // Une ligne dans la boite : "- archivees: Commande [0..*]"
    @UMLAssociation(target = Commande.class, targetMultiplicity = "0..*",
                    notation = UMLNotation.ATTRIBUTE)
    private List<Commande> archivees;
}
\end{lstlisting}

\paragraph{Ce que la notation \texttt{ATTRIBUTE} retient.} Trois paramètres : \texttt{target} donne le \textbf{type} affiché (la classe visée, et non \texttt{List}) ; \texttt{targetMultiplicity} la \textbf{multiplicité} entre crochets ; \texttt{targetRole} le \textbf{nom} de la propriété, à défaut celui de l'attribut Java. S'y ajoutent la visibilité et \texttt{\{static\}}, la barre oblique de \texttt{@UMLDerived}, puis les \texttt{@UMLConstraint}. Les paramètres qui décorent un \textit{trait} --- \texttt{type}, \texttt{sourceMultiplicity}, \texttt{sourceRole}, \texttt{label}, \texttt{direction} --- ne sont pas dessinés, et le compilateur les nomme un à un. La classe visée doit porter \texttt{@UMLClass} dans les deux notations.

\begin{lstlisting}
@UMLConstraint(rule = "ordered")
@UMLConstraint(rule = "non vide")
@UMLDerived
@UMLAssociation(target = Commande.class, targetMultiplicity = "1..*",
                notation = UMLNotation.ATTRIBUTE)
protected List<Commande> achats;
// Ligne produite : # /achats: Commande [1..*] {ordered} {non vide}
\end{lstlisting}

\subsection{Deux attributs qui se font face ne sont qu'une association}
\label{sec:reciproques}

\texttt{Eleve} cite \texttt{Cours}, et \texttt{Cours} cite \texttt{Eleve} : UML n'y voit qu'\textbf{une} association, dont chaque extrémité est nommée par la classe d'en face. Traduits séparément, les deux attributs donneraient deux traits parallèles :

\begin{lstlisting}[language=]
Eleve --> "cours 0..*" Cours        % ce que disait Eleve
Cours --> "inscrits 1..*" Eleve     % ce que disait Cours
\end{lstlisting}

La paire est fusionnée au rendu, et le dessin porte le trait unique qu'UML décrit :

\begin{lstlisting}[language=]
Eleve "inscrits 1..*" --> "cours 0..*" Cours
\end{lstlisting}

Elle n'a lieu que si le second lien \textbf{n'ajoute rien qu'un rôle et une multiplicité} --- une extrémité source ne sait pas porter davantage --- et si le premier n'a pas écrit son côté source ; sinon les deux traits restent, et un avertissement les nomme.

\section{La Classe d'Association : \texttt{@UMLAssociationClass}}

Identifie une classe comme porteuse des attributs d'une relation entre deux autres (table de jointure enrichie) : une ligne en pointillés relie le lien principal à la classe.

Paramètres : \texttt{source} et \texttt{target} (Class), les deux extrémités, toutes deux \textbf{obligatoires}. Les déclarer suffit à tracer le lien ; y ajouter une \texttt{@UMLAssociation} entre \texttt{source} et \texttt{target} dessinerait un second trait. Les deux extrémités doivent porter \texttt{@UMLClass}, et la classe annotée aussi ; aucune extrémité ne peut être la classe d'association elle-même, mais toutes deux peuvent désigner \textit{la même} classe.

\begin{lstlisting}
@UMLAssociationClass(source = Etudiant.class, target = Cours.class)
@UMLClass
public class Inscription {
    private LocalDate dateInscription;
    private double noteObtenue;
}
\end{lstlisting}

\section{La Multiplicité d'une propriété : \texttt{@UMLMultiplicity}}
\label{sec:multiplicite}

Déclare combien d'objets une propriété tient, entre crochets à côté de son nom : sur un attribut, le nombre d'objets tenus ; sur une méthode, le nombre d'objets rendus --- c'est le seul moyen de qualifier une méthode.

\begin{lstlisting}
@UMLClass(strategy = UMLVisibility.PRIVATE)
public class CanonicalMnemonic {
    @UMLMultiplicity("0..*")
    private String deprecatedAliases;   // - deprecatedAliases: String [0..*]

    @UMLMultiplicity("0..1")
    private int ucp;                    // - ucp: int [0..1]

    @UMLMultiplicity("0..*")
    public String names() { ... }       // + names(): String [0..*]
}
\end{lstlisting}

\texttt{value} (String) : la multiplicité, dans le vocabulaire d'UML --- \texttt{"1"}, \texttt{"0..1"}, \texttt{"*"}, \texttt{"1..*"}, \texttt{"2..5"} ; le nom \texttt{value} permet la forme courte \texttt{@UMLMultiplicity("0..*")}. Elle vise les propriétés qui n'ont \textbf{aucune classe à l'autre bout} : la multiplicité d'un \textit{lien} se déclare par \texttt{targetMultiplicity}, et cumuler les deux est une erreur. Avec \texttt{@UMLDerived} et \texttt{@UMLConstraint} la combinaison est libre : \texttt{- /etiquettes: String [1..*] \{sans doublon\}}.

\paragraph{Ce que le projet peut traduire à sa place.} La règle \texttt{"multiplicity": "brackets"} transcrit ce que le type dit déjà : \texttt{Optional<X>} vaut « zéro ou un », \texttt{Set<X>} « zéro ou plusieurs ». Elle ne dit jamais \textit{plus} que le type --- \texttt{0..*} et non \texttt{1..*} --- et l'annotation l'emporte sur elle. Un type enveloppe redevient alors primitif : \texttt{Optional<Integer>} s'écrit \texttt{int [0..1]}.

% ---------------------------------------------------------
\section{Les Éléments Dérivés : \texttt{@UMLDerived}}

Indique qu'un attribut, une méthode ou une association est dérivé --- calculé, non stocké. UML le note d'un slash (\texttt{/}), que l'annotation demande au rendu puisque Java ne l'accepte pas dans un identifiant. Elle ne s'applique pas à une classe. \textbf{Aucun paramètre.}

La barre oblique appartient au \textbf{nom} de la propriété, et à lui seul : sur un lien dessiné en trait elle précède le rôle cible, dans une boîte le nom de la ligne.

\begin{lstlisting}
@UMLClass(strategy = UMLVisibility.PRIVATE)
public class Personne {
    private LocalDate dateNaissance;

    @UMLDerived
    private int age; // Affiche en UML sous la forme : - /age: int

    @UMLDerived
    @UMLAssociation(target = Commande.class, targetRole = "encours",
                    targetMultiplicity = "0..*")
    private List<Commande> commandesEnCours; // Trait portant "/encours 0..*"

    @UMLDerived
    @UMLAssociation(target = Commande.class, targetMultiplicity = "0..*",
                    notation = UMLNotation.ATTRIBUTE)
    private List<Commande> commandesSoldees; // - /commandesSoldees: Commande [0..*]
}
\end{lstlisting}

% ---------------------------------------------------------
\section{Les Contraintes Métier : \texttt{@UMLConstraint}}
\label{sec:contrainte-position}

Ajoute une règle formelle, écrite entre accolades \texttt{\{ \}}, sur une classe, un attribut ou un lien (\texttt{\{subset\}}, « solde positif »). \texttt{rule} (String) : la règle, \textbf{écrite nue}, les accolades étant ajoutées par le générateur. Annotation \textbf{répétable}. Trois positions :
\begin{itemize}
    \item \textbf{sur un attribut} : à la suite de sa ligne --- \texttt{- solde: double \{toujours positif\}} ;
    \item \textbf{sur un attribut porteur de \texttt{@UMLAssociation}} : là où l'association est dessinée --- à l'extrémité cible du trait sous \texttt{ARROW}, à la fin de la ligne sous \texttt{ATTRIBUTE} ---, après la multiplicité ;
    \item \textbf{sur une classe} : dans une bulle accolée à la boîte.
\end{itemize}

\begin{lstlisting}
public class CompteBancaire {

    @UMLConstraint(rule = "solde >= decouverAutorise")
    private double solde; // Affichera {solde >= decouverAutorise} a cote de l'attribut
}
\end{lstlisting}

% ---------------------------------------------------------
\section{Les Liens Transversaux : \texttt{@UMLDependency}}

Déclare une dépendance vers une classe qui n'est pas un attribut --- utilisée localement dans une méthode. C'est la seule façon de révéler qu'une classe en utilise une autre sans en stocker l'état, le corps des méthodes ayant disparu à la compilation. Paramètres : \texttt{target} (Class) et \texttt{label} (String), la raison du lien. Annotation \textbf{répétable}.

\begin{lstlisting}
@UMLDependency(target = ServiceBancaire.class, label = "facture via")
public class Panier {
    public void valider() {
        ServiceBancaire sb = new ServiceBancaire();
        sb.payer();
    }
}
\end{lstlisting}

% ---------------------------------------------------------
\section{La Documentation Visuelle : \texttt{@UMLNote}}

Génère une bulle de commentaire rattachée à une classe, un attribut ou une méthode. Annotation \textbf{répétable}. \texttt{text} (String) : le contenu, obligatoire et non vide. \texttt{direction} (Enum) : \texttt{UMLDirection} --- \texttt{NONE}, le défaut, place la bulle \textbf{à droite} ; \texttt{UP} et \texttt{DOWN} au-dessus et en dessous.

\paragraph{Ce à quoi une note peut s'accrocher.} Une bulle ne se dessine qu'attachée à un élément présent. Deux cas la laissent sans support, et le compilateur avertit : le \textbf{membre visé n'est pas affiché} ; ou l'\textbf{attribut visé porte une \texttt{@UMLAssociation} dessinée en trait} --- les notes rattachées à un lien sont hors périmètre, et poser la note sur la classe est alors la seule façon d'en parler. Sous \texttt{ATTRIBUTE}, la note s'accroche à la ligne, en visant le \textbf{nom affiché}.

\begin{lstlisting}
public class MoteurDeRecherche {
    @UMLNote(text = "Algorithme critique, ne pas modifier", direction = UMLDirection.RIGHT)
    public void indexer() {
    }
}
\end{lstlisting}

% ---------------------------------------------------------
\section{Le Regroupement Logique : \texttt{@UMLPackage}}

Regroupe visuellement des classes dans un rectangle nommé. \texttt{name} (String), \textbf{obligatoire}, fait l'identité du groupe : deux classes déclarant le même \texttt{name} entrent dans le même rectangle. \texttt{color} (String) : couleur de fond, écrite comme celle d'une boîte.

Le groupe est déclaré, jamais déduit du paquetage Java : deux classes de paquetages différents peuvent figurer dans le même rectangle, et inversement. Il ne change rien d'autre --- les boîtes sont écrites à l'identique et les traits continuent de le traverser.

\begin{lstlisting}
@UMLPackage(name = "Module Paiement", color = "#EEEEEE")
@UMLClass
public class Facture {
}
\end{lstlisting}

% ---------------------------------------------------------
\section{Les règles du projet : le fichier \texttt{umlg.json}}
\label{sec:regles-projet}

\subsection{Principe}
Ce qui vaut pour le projet entier --- « dans ce diagramme, un \texttt{ImmutableList} s'affiche \texttt{List} » --- se déclare dans un fichier facultatif, \texttt{umlg.json}, posé \textbf{à la racine du répertoire analysé} ; pour un projet Maven ordinaire, \texttt{src/main/resources/umlg.json} (section \ref{sec:ou-regles}).

\subsection{Le partage avec les annotations}
\label{sec:partage}

Le critère est unique :

\begin{center}
\textit{Cette décision désigne-t-elle un élément par son nom ?}
\end{center}

Si oui, c'est une annotation ; si non, c'est une règle. D'où : aucune règle ne désigne un membre nommément (\texttt{"hide": ["Representation.string"]} n'existe pas), n'en range un dans un rectangle (pas de clé \texttt{group}), ni ne fabrique une boîte ou un lien. Et une priorité sans exception : \textbf{l'annotation l'emporte toujours sur la règle} --- \texttt{@UMLInclude} ramène ce qu'un \texttt{hide} écarte, \texttt{@UMLMultiplicity} l'emporte sur \texttt{"multiplicity": "brackets"}, \texttt{@UMLClass(strategy)} sur \texttt{strategy}.

\begin{center}
\begin{tabular}{@{}L{7.3cm}L{9.3cm}@{}}
\hline
\textbf{Ce qu'on veut} & \textbf{Où cela s'écrit} \\
\hline
Renommer une boîte & \texttt{@UMLClass(name = ...)} \\
Renommer un membre & \texttt{@UMLInclude(name = ...)} \\
Taire un membre précis & \texttt{@UMLExclude} \\
Ranger des classes dans un rectangle & \texttt{@UMLPackage(name = ...)} \\
\hline
\end{tabular}
\end{center}

\subsection{Forme du fichier et vocabulaire}
\label{sec:vocabulaire}
Un \textbf{objet JSON}, dont chaque clé dit une nature de règle, encodé en \textbf{UTF-8}. Le vocabulaire est \textbf{fermé} : une clé inconnue arrête la génération. Un fichier vide, ou réduit à \texttt{\{\}}, ne règle rien ; écrire le défaut est permis (\texttt{"order": "alphabetical"}). Onze clés, et \textbf{aucune} qui refasse ce qu'une annotation sait faire. Dans le tableau, ce qui est en \texttt{chasse fixe} s'écrit tel quel, ce qui est en \meta{italique entre chevrons} est à remplacer, et une barre verticale sépare des valeurs au choix.

\begin{longtable}{@{}L{7.4cm}L{9.2cm}@{}}
\hline
\textbf{Forme de la règle} & \textbf{Ce qu'elle fait} \\
\hline
\endhead
\texttt{"hide": [}\meta{motif}\texttt{, }\meta{motif}\texttt{...]} & Écarte les \textbf{membres} --- méthodes comme attributs --- dont le nom suit l'un des motifs, où \texttt{*} remplace n'importe quelle suite de caractères. Ex. : \texttt{["get*", "log", "*Cache"]} \\
\texttt{"omit": [}\meta{"visibility" | "parameter names" | "return void" | "abstract"}\texttt{, ...]} & Retire un morceau de la ligne : les symboles \texttt{+ - \# \textasciitilde} ; les noms des paramètres (\texttt{from(KeyboardMap)}) ; le type rendu \texttt{void} ; la marque \texttt{\{abstract\}} --- le mot-clé de la boîte, lui, reste écrit. \\
\texttt{"strategy": }\meta{"none" | "public" | "protected" | "package" | "private"} & La stratégie des classes qui ne déclarent pas la leur. \\
\texttt{"types": \{ }\meta{type du code}\texttt{: }\meta{nom affiché}\texttt{, ... \}} & Renomme \textit{n'importe quel} type dans les boîtes, chevrons compris. \\
\texttt{"order": }\meta{"declaration" | "alphabetical"} & L'ordre des membres ; \texttt{"alphabetical"} est le défaut. \\
\texttt{"multiplicity": "brackets"} & \texttt{Set<X>} s'écrit \texttt{X [0..*]}, \texttt{Optional<X>} \texttt{X [0..1]}. \\
\texttt{"title": }\meta{texte libre} & Titre de la vue intégrale, pris tel quel. \\
\texttt{"direction": }\meta{"top-to-bottom" | "left-to-right"} & Son sens de lecture. \\
\texttt{"showEmptyMembers": true} & Rétablit les compartiments vides. \\
\texttt{"views": [ \{ "name": }\meta{nom}\texttt{, "retain": [}\meta{sélecteur}\texttt{, ...] \} ]} & Déclare une vue et ce qu'elle retient, dans l'ordre. Deux clés facultatives dans le même objet : \texttt{"remove"}, ce qu'elle retire de ce qu'elle a retenu, et \texttt{"direction"}, son sens de lecture. \\
\texttt{"viewsByPackage": true} & Une vue par paquetage, sans rien déclarer. \\
\hline
\end{longtable}

\noindent Un \meta{sélecteur} s'écrit de trois façons, et de trois seulement : une \textbf{chaîne} pour une classe, par son nom simple ou complet ; \texttt{\{ "package": }\meta{paquetage}\texttt{ \}} ; \texttt{\{ "around": }\meta{Classe}\texttt{ \}} (section \ref{sec:vues}). Un \meta{motif} et un \meta{nom de type} ne sont contraints par aucune liste : ce sont les noms du projet analysé.

\paragraph{Les commentaires.} JSON n'en a pas : une clé dont le nom commence par \texttt{\_} n'est pas une règle et n'est \textbf{pas lue}, dans l'objet de tête comme dans une vue.

\begin{lstlisting}[language=]
{
  "_": "Les types de Guava n'apprennent rien au lecteur du diagramme.",
  "_pourquoi": "Une seconde note ne gene pas la premiere.",
  "types": { "ImmutableList": "List" }
}
\end{lstlisting}

\subsection{Chaque clé par l'exemple}
\label{sec:exemples-regles}

\paragraph{\texttt{strategy}.} La stratégie des classes dont le \texttt{strategy} vaut \texttt{PROJECT}, c'est-à-dire le défaut de \texttt{@UMLClass}. Sans cette clé, aucun membre n'est dessiné et les boîtes sortent vides --- ce que la génération \textbf{signale} ; un \texttt{"none"} \textbf{écrit} donne le même dessin sans le signalement.

\begin{lstlisting}[language=]
"strategy": "public"
"_autres": "none, protected, package, private"
\end{lstlisting}

\paragraph{\texttt{hide}.} Un tableau de \textbf{motifs de noms}, un par entrée. L'étoile remplace n'importe quelle suite de caractères, y compris aucune ; tout le reste est pris au pied de la lettre, et la casse compte.

\begin{lstlisting}[language=]
"hide": ["get*", "set*", "is*", "toString", "hashCode",
         "with*", "visit*", "*Cache"]
\end{lstlisting}
Un motif ne regarde que le \textbf{nom}, jamais la signature : \texttt{"get*"} emporte aussi un \texttt{getPrix(Client)} métier, que \texttt{@UMLInclude} ramène. Il vise \textbf{méthodes et attributs indifféremment}, et l'étoile s'écrit : \texttt{"get"} ne masque que le membre nommé exactement \texttt{get}. Un motif qui n'a rien masqué est signalé en fin de génération.

\paragraph{\texttt{omit}.} Ces réglages ne font disparaître aucun membre : ils retirent \textbf{un morceau de la ligne} d'un membre qui reste affiché, et aucun \texttt{@UMLInclude} ne les contredit. \texttt{"return void"} ne vaut que pour le retour, et que pour \texttt{void} : un type de retour utile n'est jamais effacé.

\begin{lstlisting}[language=]
"_omit": "visibility     : 'valider()' et non '+ valider()'
          parameter names: 'from(KeyboardMap)' et non 'from(m : KeyboardMap)'
          return void    : 'valider()' et non 'valider() : void'",
"omit": ["visibility", "parameter names", "return void"]
\end{lstlisting}

\paragraph{\texttt{types}.} Remplace un nom de type par un autre, \textbf{partout où ce type paraît dans une boîte} : attributs, types de retour, paramètres, chevrons compris. Le nom du code étant une \textbf{clé}, deux règles contradictoires sur le même type sont refusées par l'analyseur lui-même. Il s'écrit au choix simple ou complet, le nom complet l'emportant --- de quoi viser une classe précise quand deux paquetages en ont une homonyme. La règle ne touche pas le \textbf{nom d'une boîte}, qui relève de \texttt{@UMLClass(name)}.

\begin{lstlisting}[language=]
"_types": "'ImmutableList<ImmutableSet<String>>' s'ecrit 'List<Set<String>>'",
"types": {
  "ImmutableList": "List",
  "com.google.common.collect.ImmutableSet": "Set"
}
\end{lstlisting}

\paragraph{\texttt{order} et \texttt{multiplicity}.}
\begin{lstlisting}[language=]
"_order": "L'ordre du source ; le defaut est 'alphabetical'.",
"order": "declaration",

"_multiplicity": "Set<String> aliases   ->  aliases : String [0..*]
                  Optional<Integer> ucp ->  ucp : int [0..1]",
"multiplicity": "brackets"
\end{lstlisting}

\paragraph{\texttt{title}, \texttt{direction}, \texttt{showEmptyMembers}.} Le titre est pris tel quel, espaces compris. Sans stratégie déclarée une boîte n'a aucun membre, et rétablir les compartiments vides dessinerait deux rectangles vides sous chaque nom.
\begin{lstlisting}[language=]
"title": "Architecture du module Facturation",
"direction": "left-to-right",
"_direction": "aussi : top-to-bottom, le defaut",
"showEmptyMembers": true
\end{lstlisting}

\paragraph{\texttt{views} et \texttt{viewsByPackage} :} détaillés en section \ref{sec:vues}.

\subsection{Le fichier minimal}
Trois clés suffisent au cas nominal :
\begin{lstlisting}[language=]
{
  "strategy": "public",
  "hide": ["get*", "set*"],
  "types": { "ImmutableList": "List" }
}
\end{lstlisting}

\subsection{Un fichier complet}
\begin{lstlisting}[language=]
{
  "_dessin": "---- Le dessin d'ensemble ----",
  "title": "Architecture du module Facturation",
  "direction": "left-to-right",

  "_boites": "---- Ce que les boites montrent ----",
  "strategy": "public",
  "hide": ["get*", "set*", "is*", "toString", "hashCode", "equals",
           "with*", "visit*", "log", "LOGGER"],
  "omit": ["return void", "visibility", "parameter names"],
  "order": "declaration",
  "multiplicity": "brackets",
  "types": { "ImmutableList": "List" },

  "_vues": "---- Les vues ----",
  "views": [
    { "name": "Le domaine",
      "retain": [{ "package": "com.exemple.modele" }] },
    { "name": "Facturation",
      "retain": ["Facture", "LigneFacture", "Client"],
      "direction": "left-to-right" },
    { "name": "Autour de Facture",
      "retain": [{ "around": "Facture" }] }
  ],
  "viewsByPackage": true
}
\end{lstlisting}

\subsection{Ce qui est refusé}
Chaque refus nomme le fichier, le \textbf{chemin fautif} --- \texttt{views[1].direction}, \texttt{omit[0]} --- et la forme attendue, et \textbf{arrête la génération} plutôt que d'appliquer le fichier à moitié ; les fautes de syntaxe gardent le numéro de ligne. Sont refusés : un JSON mal formé (virgule finale, accolade oubliée) ou un fichier qui n'est pas en UTF-8 --- un \texttt{\#} de commentaire échoue ici, une note s'écrivant dans une clé \texttt{\_} ; une valeur qui n'est pas de la sorte attendue, \texttt{"hide": "get*"} au lieu d'un tableau ; une clé inconnue (\texttt{"couleur"}), une valeur inconnue d'un \texttt{omit}, \texttt{order}, \texttt{direction} ou \texttt{multiplicity}, une stratégie inconnue ou \texttt{"strategy": "project"} ; une clé écrite deux fois, ou deux fois la même valeur dans \texttt{omit} ; un \texttt{title} vide, un motif vide ou réduit à \texttt{*}, une moitié vide d'un \texttt{types} ; un motif contenant un point (\texttt{"Representation.string"}), pour lequel \texttt{@UMLExclude} est fait ; une espace au milieu d'un motif, d'un nom de type ou d'un sélecteur ; une vue sans \texttt{name} ou sans \texttt{retain}, un \texttt{retain} vide, une vue déclarée deux fois, une clé inconnue dans une vue ; un sélecteur ne désignant aucune classe.

Une entrée syntaxiquement correcte dont le nom ne correspond à rien --- \texttt{"ImutableList": "List"}, le motif \texttt{"LOGGR"}, l'étoile oubliée d'un \texttt{"get"} --- n'est pas refusée : la génération relève en fin de scan les entrées restées sans effet et les signale (section \ref{sec:avertissements-generation}).

% ---------------------------------------------------------
\section{L'apparence du diagramme : \texttt{UmlStyle}}
\label{sec:style}

L'habillage --- couleurs des boîtes, épaisseur et teinte des traits, police --- se déclare \textbf{à l'appel du générateur}, par \texttt{.style(UmlStyle.UMLG)} sur le builder (section \ref{sec:sortie}). Deux valeurs, et aucun accès aux \texttt{skinparam}. Deux réglages y échappent : les visibilités sont écrites \texttt{+}, \texttt{-}, \texttt{\#}, \texttt{\textasciitilde} plutôt qu'en pastilles colorées (\texttt{classAttributeIconSize 0}), et l'\textbf{espacement} est calculé sur la plus longue étiquette du diagramme.

\begin{center}
\begin{tabular}{@{}L{2.9cm}L{6.0cm}L{7.6cm}@{}}
\hline
\textbf{Valeur} & \textbf{Ce qui est dessiné} & \textbf{Quand la choisir} \\
\hline
\texttt{PLANTUML} \newline \small(défaut) & Boîtes grises, pastille \texttt{C} ou \texttt{I}, traits par défaut. & Le cas nominal : le rendu que l'utilisateur reconnaît. \\[0.4em]
\texttt{UMLG} & Bandeau bleu pâle sur fond blanc cassé, bords bleu foncé, coins arrondis, pas d'ombre, nom des liens en italique coloré, pastille masquée. & À l'impression, ou sur un fond clair. \\
\hline
\end{tabular}
\end{center}

% ---------------------------------------------------------
\section{Les vues : plusieurs diagrammes pour un projet}
\label{sec:vues}

\subsection{Principe}
La bibliothèque produit, en une exécution, \textbf{un dossier de diagrammes} plutôt qu'une image :

\begin{lstlisting}[language=]
diagrammes/
|-- projet.svg          <- la vue integrale, toujours produite
`-- vues/
    |-- le-domaine.svg
    |-- autour-de-compte.svg
    `-- com.banque.modele.svg
\end{lstlisting}

La \textbf{vue intégrale} est toujours écrite à la racine, et porte le titre et le sens de lecture déclarés par \texttt{title} et \texttt{direction}. Les autres vivent dans un sous-dossier ; chacune porte son propre titre --- son nom --- et son propre sens de lecture.

\subsection{Déclarer une vue}
Une vue tient dans un objet : son nom, ce qu'elle retient dans l'ordre où on veut le lire, ce qu'elle retire, son sens de lecture.
\begin{lstlisting}[language=]
"views": [
  { "name": "Le domaine",
    "retain": [{ "package": "com.banque.modele" }] },
  { "name": "Facturation",
    "retain": ["Facture", "LigneFacture", "Client"],
    "direction": "left-to-right" },
  { "name": "Autour de Compte",
    "retain": [{ "around": "Compte" }] },
  { "name": "Le domaine sans les lecteurs",
    "retain": [{ "package": "com.banque" }],
    "remove": ["XkbSymbolsReader"] }
]
\end{lstlisting}

Trois façons de désigner des classes, et trois seulement :
\begin{center}
\begin{tabular}{@{}L{4.0cm}L{12.5cm}@{}}
\hline
\textbf{Sélecteur} & \textbf{Ce qu'il retient} \\
\hline
\texttt{"Facture"} & Une classe, par son nom simple ou complet. \\[0.4em]
\texttt{\{ "package": "com.exemple" \}} & Toutes les classes du paquetage, correspondance exacte --- un sous-paquetage n'entre pas. \\[0.4em]
\texttt{\{ "around": "Facture" \}} & La classe et ses voisines immédiates ; le rayon est de un. \\
\hline
\end{tabular}
\end{center}

\paragraph{Un voisinage peut être vide.} Les voisins d'\texttt{around} sont les extrémités des \textbf{relations déclarées} --- \texttt{@UMLAssociation}, \texttt{@UMLDependency}, héritages entre classes annotées --- et non les types que le code manipule : une classe très entourée peut n'avoir aucun voisin déclaré, et la vue se réduit alors à une boîte seule, ce dont la génération \textbf{avertit}. Un sélecteur qui ne désigne \textit{aucune} classe, lui, arrête la génération.

\subsection{L'ordre d'écriture est l'ordre de lecture}
Les classes d'une vue sont dessinées dans l'ordre où elles sont écrites : le moteur place déjà ce qui est relié, mais ne peut pas deviner l'ordre de deux boîtes que \textit{rien} ne relie. La bibliothèque enchaîne donc par un lien invisible les \textbf{blocs} de la vue --- un bloc étant un groupe de boîtes que les traits relient, de proche en proche --- dans l'ordre où leur première boîte est écrite. Un sélecteur \texttt{"package"} ou une vue calculée ne portent aucun ordre : leurs boîtes sont rangées par nom complet.

\subsection{Les vues calculées}
\begin{lstlisting}[language=]
"viewsByPackage": true
\end{lstlisting}
Une vue par paquetage Java, sans rien déclarer --- mais retenant \textit{tout} le paquetage, là où un auteur en écarterait les classes techniques.

\subsection{Les liens sortants, le passage d'une vue à l'autre, les proportions}
Une relation dont l'autre bout n'est pas dans la vue \textbf{disparaît, sans un mot} : la boîte manquante n'est jamais ajoutée pour sauver le trait. Chaque boîte porte en revanche un \textbf{lien cliquable} vers la première vue déclarée qui la retient ; une vue ne renvoie jamais vers elle-même, et les chemins sont relatifs, si bien que le dossier reste déplaçable.

Une vue dont les boîtes s'alignent sur une seule rangée donne un ruban illisible. Deux garde-fous : \textbf{l'enchaînement des blocs s'arrête à trois} ; et les \textbf{proportions sont mesurées} --- la bibliothèque relit les dimensions de ce qu'elle vient d'écrire et \textbf{avertit} lorsque le rapport dépasse quatre pour un, sans rien corriger.

\subsection{Ce que la génération dit d'elle-même}
\begin{lstlisting}[language=]
12 diagram(s) written to /chemin/diagrammes
  21 class(es) drawn, 23 ignored (no @UMLClass)
\end{lstlisting}

Sous une douzaine, les classes ignorées sont nommées ; au-delà, la génération écrit \texttt{ignored-classes.txt} à la racine de la sortie. Le compte rendu est \textbf{rendu, non imprimé} : \texttt{generate()} rend le \texttt{RapportDeGeneration}, que la ligne de commande écrit sur la sortie standard et le plugin Maven passe à son log --- les avertissements de même. Chaque image est enfin accompagnée de sa \textbf{source PlantUML}, sous le même nom et l'extension \texttt{.puml}.

\subsection{Ce que la génération signale}
\label{sec:avertissements-generation}
Un \textbf{avertissement} dit que le diagramme est \textit{exact}, mais qu'il montre moins que ce que son auteur croit avoir demandé ; chacun se tait dès qu'un choix explicite a été écrit.

\begin{longtable}{@{}L{6.3cm}L{10.3cm}@{}}
\hline
\textbf{Situation} & \textbf{Ce que l'auteur découvrirait sinon sur l'image} \\
\hline
\endhead
Des boîtes sans membre, aucune \texttt{strategy} déclarée nulle part & Le défaut ne dessine aucun membre. Le message nomme les boîtes et les trois remèdes ; il se tait devant un \texttt{"strategy": "none"} \textbf{écrit}. \\[0.4em]
Aucun paramètre d'aucune méthode ne porte de nom & Projet compilé sans \texttt{-parameters} (section \ref{sec:membres}). \\[0.4em]
Des \texttt{.class} que le chargeur n'a pas su lier & Dépendance absente du classpath, ou compilation partielle. Ces classes sont écartées et nommées ; rien ne dit si elles portaient \texttt{@UMLClass}. \\[0.4em]
Deux boîtes portant le même nom affiché & Deux classes homonymes : les traits aboutissent à la bonne boîte, mais le lecteur voit deux rectangles identiques. \\[0.4em]
Une vue \texttt{"around"} sans voisin & Les voisins viennent des relations déclarées, pas des types du code. \\[0.4em]
Une règle de nommage restée lettre morte & Une entrée de \texttt{types} ou un motif de \texttt{hide} qui n'a rien touché : faute de frappe, ou étoile oubliée. \\[0.4em]
Une vue aux proportions illisibles & Le ruban décrit ci-dessus. \\
\hline
\end{longtable}

\paragraph{Ce qui arrête la génération.} Une annotation contradictoire, une couleur inconnue de PlantUML, un fichier de règles fautif, une vue nommant une classe absente, un répertoire où aucune classe ne porte \texttt{@UMLClass} --- et \textbf{Graphviz introuvable} : PlantUML dessinerait alors une image portant « Cannot find Graphviz » que rien ne distingue d'un dessin réussi, aussi le moteur est-il vérifié avant de dessiner.

\subsection{La sortie : destination, format, génération précédente}
\label{sec:sortie}
\begin{lstlisting}
UMLGenerator.builder()
    .sourceDirectory("target/classes")
    .outputDirectory("diagrammes")  // toutes les vues ; outputFile n'ecrit
    .outputFormat(".svg")           //   que le diagramme d'ensemble
    .keepPrevious(true)             // facultatif ; false par defaut
    .style(UmlStyle.UMLG)           // facultatif ; PLANTUML par defaut
    .build()
    .generate();
\end{lstlisting}
Par défaut, les diagrammes précédents sont effacés, de sorte que le dossier décrive l'état courant du code ; seuls les fichiers que la bibliothèque écrit sont retirés. Sous \texttt{keepPrevious}, la génération va dans un dossier voisin numéroté --- \texttt{diagrammes-2}, \texttt{diagrammes-3}.

\paragraph{En ligne de commande.}
\begin{lstlisting}[language=]
UMLGenerator <repertoire-analyse> [fichier.svg|dossier] [png|svg]
\end{lstlisting}
Un second argument finissant par \texttt{.svg} ou \texttt{.png} demande ce seul fichier ; tout autre nom demande un dossier de vues.

\paragraph{Depuis Maven}, la forme à préférer : le plugin \texttt{umlg-maven-plugin} et son goal \texttt{generate} (section \ref{sec:modedemploi}), qui transmet en outre le \textbf{classpath d'exécution} du projet --- charger une classe résout son parent, lire un attribut résout son type.

\section{La vérification à la compilation}
\label{sec:verification}

\subsection{Principe}
La bibliothèque embarque un \textbf{processeur d'annotations} (JSR 269) qui s'exécute à l'intérieur de \texttt{javac} : il n'engendre aucun fichier, il lit les annotations et pointe la valeur en cause dans le source. Il construit les objets du modèle avec les valeurs lues et traduit en erreur de compilation l'exception que le modèle lève déjà ; le message de \texttt{javac} est donc mot pour mot celui que la génération aurait produit. Deux gravités :
\begin{itemize}
    \item \textbf{Erreur} : \textit{ce code ne décrit aucun diagramme}. La compilation s'arrête.
    \item \textbf{Avertissement} : \textit{ce code décrit un diagramme, mais vraisemblablement pas celui que son auteur croit}. La compilation continue --- l'annotation fait toujours foi.
\end{itemize}

\subsection{Ce qui arrête la compilation}
\begin{itemize}
    \item cible d'un lien dépourvue de \texttt{@UMLClass}, cible primitive (\texttt{int.class}) ou qui n'est pas une classe ;
    \item annotation de lien posée sur une classe dépourvue de \texttt{@UMLClass} ;
    \item multiplicité illisible (\texttt{"beaucoup"}) ou inversée (\texttt{"3..1"}) ;
    \item couleur inconnue de PlantUML ;
    \item texte fait uniquement d'espaces (nom, rôle, label, stéréotype, titre), ou \texttt{@UMLPackage(name)} vide ;
    \item \texttt{@UMLInclude(name)} et \texttt{targetRole} sur la même ligne ;
    \item \texttt{@UMLInclude} et \texttt{@UMLExclude} sur le même membre ;
    \item \texttt{@UMLMultiplicity} et \texttt{@UMLAssociation} sur le même attribut ;
    \item \texttt{asAttribute = true} sur une méthode à paramètres, sur une méthode \texttt{void}, ou sur un attribut ;
    \item \texttt{@UMLAssociationClass} dont une extrémité est la classe annotée ;
    \item dépendance d'une classe vers elle-même, ou deux fois la même.
\end{itemize}

\subsection{Ce qui produit un avertissement}
\begin{longtable}{@{}L{6.6cm}L{10.0cm}@{}}
\hline
\textbf{Situation} & \textbf{Ce que l'auteur attendait, et n'aura pas} \\
\hline
\endhead
\texttt{@UMLInclude} sur un membre déjà affiché, \texttt{@UMLExclude} sur un membre déjà masqué, \texttt{@UMLInclude(name)} reprenant le nom du code & La dérogation ne déroge à rien, le renommage n'a pas eu lieu. Un \texttt{name} qui renomme vraiment n'est jamais signalé. \\
\texttt{@UMLInclude} ou \texttt{@UMLExclude} sur un attribut porteur de \texttt{@UMLAssociation} & Sous \texttt{ARROW} l'attribut est un lien --- rien ne l'y ramène, et l'exclure supprime le \textbf{trait} ; sous \texttt{ATTRIBUTE} il est déjà affiché, et c'est la \textbf{ligne} qui disparaît. \\
Paramètre de trait écrit sous \texttt{notation = ATTRIBUTE} (\texttt{type}, \texttt{label}, \texttt{direction}, \texttt{sourceRole}, \texttt{sourceMultiplicity}) & Ces valeurs ne seront dessinées nulle part ; le message les nomme une à une. \\
\texttt{stereotype} contenant déjà \texttt{<<~>>}, ou \texttt{rule} portant déjà ses accolades & Elles seraient dessinées en double. \\
Deux classes affichant la même étiquette, ou deux couleurs pour un même groupe & Deux rectangles que le lecteur ne peut pas distinguer ; pour la couleur, la première l'emporte. \\
\texttt{@UMLDependency} vers une classe déjà atteinte par une association \textbf{dessinée en trait} & Une association dit strictement plus qu'une dépendance. Sous \texttt{ATTRIBUTE}, rien n'est signalé. \\
Attribut de type collection sans \texttt{targetMultiplicity}, ou multiplicité que le type contredit (\texttt{List} pour \texttt{"0..1"}) & Aucune multiplicité ne sera portée, ou bien l'un des deux se trompe. \\
\texttt{target} absent du type de l'attribut & Le lien sera tout de même dessiné vers la classe déclarée. \\
\texttt{@UMLDerived}, \texttt{@UMLMultiplicity}, \texttt{@UMLNote} ou \texttt{@UMLConstraint} sur un membre que le diagramme n'affiche pas & Barre oblique, crochets, bulle ou accolades ne se voient que si l'élément marqué est dessiné. \texttt{@UMLMultiplicity("")} ne demande rien. \\
\texttt{@UMLDerived} sur un lien \textbf{en trait} sans \texttt{targetRole} & La barre se pose devant le rôle cible ; sans rôle, rien ne peut la porter. \\
\texttt{@UMLNote} sur un attribut porteur d'une association \textbf{en trait} & Une note ne s'accroche pas à un trait. \\
\hline
\end{longtable}

Chacun de ces contrôles \textbf{se tait dès qu'il ne peut pas conclure} : une collection écrite sans paramètre de type (\texttt{List} nu) ne se voit jamais reprocher sa cible ; les \textbf{composants d'un record} échappent aux contrôles qui disent « ce membre n'est pas affiché » ; et un \texttt{@UMLInclude} qui déroge à un \texttt{hide} du projet n'est jamais « sans effet ».

\subsection{Faire taire les avertissements}
L'option \texttt{-Aumlg.warnings=none} les éteint tous ; \texttt{none} est la seule valeur reconnue, toute autre étant \textbf{refusée}, et les erreurs ne s'éteignent pas. Le silence porte sur ce que le processeur a trouvé dans le code, non sur son propre état : un \texttt{-Aumlg.rules} désignant un fichier introuvable reste signalé même sous \texttt{none}.

\subsection{Donner le fichier de règles au compilateur}
\label{sec:option-regles}
Six avertissements dépendent de la stratégie appliquée à la classe --- ceux qui disent « ce membre n'est pas affiché » ou « il l'est déjà ». Quand la classe la déclare, le processeur conclut seul ; quand elle s'en remet au projet (\texttt{PROJECT}, le défaut), la réponse est dans \texttt{umlg.json}, que \texttt{javac} ne sait pas trouver. Le processeur \textbf{se tait} alors sur ces six contrôles, à moins qu'on ne lui donne le chemin :

\begin{lstlisting}[language=XML]
<compilerArgs>
    <arg>-Aumlg.rules=src/main/resources/umlg.json</arg>
</compilerArgs>
\end{lstlisting}

Trois situations : \textbf{option absente}, le processeur se tait ; \textbf{fichier introuvable}, \textbf{avertissement} ; \textbf{fichier fautif}, \textbf{erreur}. Cette option ne change jamais le diagramme produit, et n'ajoute ni ne retire aucune \textit{erreur}.

\section{Ce qui est hors périmètre}
\label{sec:horsperimetre}

Écartés de l'API, et à ne pas réintroduire par inadvertance : le \textbf{style fin des liens} (couleur, épaisseur, pointillés, longueur) ; la \textbf{navigabilité explicite} (\texttt{-{}-} contre \texttt{-{}->} contre \texttt{<-{}->}) ; la \textbf{pastille de stéréotype} (\texttt{<<(S,\#FF7700) Service>>}) et les stéréotypes multiples ; l'\textbf{association qualifiée}, que PlantUML ne sait pas dessiner --- la donnée qui indexe se dit par le type de l'attribut ; l'\textbf{imbrication de paquetages} et les variantes de conteneurs (\texttt{namespace}, \texttt{folder}, \texttt{frame}, \texttt{together}) ; les \textbf{notes rattachées à un lien} et les notes flottantes ; les \textbf{directives brutes} \texttt{skinparam} et les thèmes PlantUML ; le \textbf{placement d'une boîte par rapport à une autre}, remplacé par l'ordre d'écriture d'une vue (section \ref{sec:vues}) ; enfin les \textbf{boîtes, attributs et liens déclarés hors du code} --- une classe encore à écrire s'écrit vide, en Java, avec \texttt{@UMLClass}.

\subsection{Ce qui relève de l'analyse automatique}
Sont déduits du code compilé, sans aucune annotation : la nature de l'entité (classe, classe abstraite, interface, énumération, type annotation, \textit{record}), les liens d'héritage lus dans \texttt{extends} et \texttt{implements}, les littéraux d'une énumération, le modificateur \texttt{static}, la visibilité de chaque membre, et les signatures de méthodes (type de retour, types des paramètres, et leurs noms sous \texttt{-parameters}). S'y ajoutent les \textbf{paramètres de type} d'une classe générique, écrits à la suite de son nom, bornes comprises --- \texttt{Boite<T>}, \texttt{Table<K, V extends Number>} --- mais distincts du nom, qui seul désigne la boîte dans un sélecteur de vue ; et l'italique d'une \textbf{opération sans corps}, \texttt{abstract} ou déclarée par une interface sans être \texttt{default}.

\subsection{Ce qui ne peut pas être déduit}
La lecture ayant lieu après compilation (section \ref{sec:lecture}), les \textbf{valeurs d'initialisation des attributs} et le \textbf{corps des méthodes} ont disparu --- d'où \texttt{@UMLDependency}. Reste réellement indéductible la \textbf{multiplicité} : rien dans \texttt{Set<String>} ne dit \texttt{0..*} plutôt que \texttt{1..*}. Le \textbf{nom des paramètres}, lui, est une option de construction du projet analysé, \texttt{-parameters}, qu'aucune annotation ne remplace.

\section{Mode d'emploi : de zéro à un dossier de diagrammes}
\label{sec:modedemploi}

\subsection{1. Déclarer la bibliothèque dans le \texttt{pom}}
Une dépendance --- les annotations, et le processeur que \texttt{javac} découvre seul dès qu'elle est sur le classpath --- et un plugin, qui apporte le goal qui dessine.

\begin{lstlisting}[language=XML]
<properties><maven.compiler.parameters>true</maven.compiler.parameters></properties>
<dependency>  <!-- les annotations, et le processeur qu'elles embarquent -->
    <groupId>io.github.oliviercailloux</groupId>
    <artifactId>umlg</artifactId> <version>1.0-SNAPSHOT</version>
</dependency>
<plugin>      <!-- le goal qui dessine -->
    <groupId>io.github.oliviercailloux</groupId>
    <artifactId>umlg-maven-plugin</artifactId> <version>1.0-SNAPSHOT</version>
    <executions><execution><goals><goal>generate</goal></goals></execution></executions>
</plugin>
<plugin>      <!-- version epinglee, sinon Maven resout la 3.1 de 2013 -->
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId> <version>3.13.0</version>
    <configuration><showWarnings>true</showWarnings></configuration>
</plugin>
\end{lstlisting}
Les trois réglages du compilateur comptent : sans \texttt{parameters}, les diagrammes écrivent \texttt{entries(String)} au lieu d'\texttt{entries(xKeyName: String)} ; sans \texttt{showWarnings}, Maven passe \texttt{-nowarn} à \texttt{javac} et fait taire le processeur, ses erreurs mises à part ; sans version \textbf{épinglée}, Maven résout la 3.1, antérieure à \texttt{parameters}, alors ignoré en silence.

\subsection{2. Annoter le code}
\texttt{@UMLClass} sur les classes à dessiner suffit à obtenir un diagramme ; les dix autres sont facultatives et se posent au fur et à mesure qu'on veut en dire plus.

\subsection{3. Poser \texttt{umlg.json} --- à un endroit précis, et à un seul}
\label{sec:ou-regles}

La bibliothèque cherche le fichier à \textbf{un seul chemin}, qu'elle calcule et ne devine pas :

\begin{center}
\meta{répertoire analysé}\texttt{/umlg.json}
\end{center}

Le \textbf{nom est fixe} --- exactement \texttt{umlg.json}, casse comprise ; la \textbf{recherche ne descend pas} dans les sous-dossiers ; et \textbf{aucune option ne le déplace} : on change le répertoire analysé, et \texttt{-Dumlg.sourceDirectory=autre/chemin} fait attendre le fichier à \texttt{autre/chemin/umlg.json}.

Or le répertoire analysé est celui des \textbf{classes compilées} --- \texttt{target/classes} par défaut --- et non celui des sources. On écrit donc le fichier là d'où la construction le \textit{recopiera} : \textbf{\texttt{src/main/resources/umlg.json}}, dont Maven recopie le contenu à la racine de \texttt{target/classes}. Il est ainsi versionné avec le code qu'il décrit. Le fichier est \textbf{facultatif} ; \textit{présent mais fautif}, il arrête la génération.

\paragraph{La seule exception.} \texttt{javac} ne connaît pas \texttt{target/classes} : le processeur reçoit le chemin \textbf{nommément} par \texttt{-Aumlg.rules=...} (section \ref{sec:option-regles}). Là, et là seulement, le chemin et le nom sont libres.

\subsection{4. Lancer}
Trois façons, la première étant celle à préférer : \textbf{depuis Maven}, \texttt{mvn compile umlg:generate} ; \textbf{en ligne de commande}, \texttt{UMLGenerator} \meta{répertoire} \texttt{[fichier.svg|dossier] [png|svg]} ; \textbf{par programme}, \texttt{UMLGenerator.builder()\ldots build().generate()} (section \ref{sec:sortie}).

Le \texttt{compile} n'est pas facultatif : rien n'est analysable tant que les \texttt{.class} ne sont pas écrits, et c'est lui qui recopie \texttt{umlg.json} au bon endroit.

\paragraph{Tout ce qui se règle à l'appel.} Six propriétés, surchargeables aussi par \texttt{<configuration>} dans le \texttt{pom} ; \texttt{umlg:help} les énumère.

\begin{itemize}
    \item \texttt{umlg.sourceDirectory} (\texttt{target/classes}) : le répertoire analysé --- et donc où \texttt{umlg.json} est cherché ;
    \item \texttt{umlg.outputDirectory} (\texttt{diagrammes/}) : le dossier écrit, à la racine du module ;
    \item \texttt{umlg.outputFile} : un seul fichier au lieu du dossier, son extension décidant du format ;
    \item \texttt{umlg.format} (\texttt{svg}) : \texttt{svg} ou \texttt{png}, pour les images du dossier ;
    \item \texttt{umlg.keepPrevious} (\texttt{false}) : écrire dans un dossier voisin numéroté plutôt qu'effacer ;
    \item \texttt{umlg.skip} (\texttt{false}) : sauter la génération sans arrêter la construction.
\end{itemize}

\noindent Les chemins relatifs s'entendent depuis la racine du module, jamais depuis le répertoire d'où Maven a été lancé. Trois lignes couvrent l'usage courant :

\begin{lstlisting}[language=]
mvn compile umlg:generate                              # le dossier, en SVG
mvn compile umlg:generate -Dumlg.format=png            # le dossier, en PNG
mvn compile umlg:generate -Dumlg.outputFile=archi.svg  # la seule vue d'ensemble
\end{lstlisting}

\subsection{5. Ce qu'on obtient}
Un dossier \texttt{diagrammes/} : la vue intégrale à sa racine, les vues dans \texttt{vues/}, la source \texttt{.puml} près de chaque image, et \texttt{ignored-classes.txt} au-delà d'une douzaine de classes écartées. Compte rendu et avertissements partent dans le log Maven, en \texttt{[WARNING]}. Le dossier vit \textbf{à la racine du projet}, non dans \texttt{target/} : c'est une documentation, faite pour être versionnée.
