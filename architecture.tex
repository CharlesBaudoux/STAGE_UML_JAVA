\section{Comment lire ce document}

Ce document répond à une seule question, fichier par fichier : \emph{pourquoi celui-là
existe-t-il, et que se passerait-il s'il n'existait pas ?} Il ne remplace pas les
spécifications des annotations (\texttt{annotation.tex}), qui décrivent ce que l'utilisateur
\emph{écrit} ; il décrit ce que la bibliothèque \emph{fait} de ce qu'il a écrit.

Le vocabulaire tient en trois mots, employés partout dans le code :

\begin{itemize}
  \item une \textbf{entité} est une classe qui apparaîtra dans le diagramme (une boîte) ;
  \item un \textbf{lien} (ou \emph{relation}) est un trait entre deux boîtes ;
  \item un \textbf{membre} est un attribut ou une méthode, écrit à l'intérieur d'une boîte.
\end{itemize}

\section{Vue d'ensemble : la chaîne de traitement}

La bibliothèque transforme du code Java annoté en une image. Ce trajet se fait en quatre
étapes, et \emph{chaque dossier correspond exactement à une étape}. C'est la clé de lecture
principale : si vous savez à quelle étape appartient un problème, vous savez dans quel dossier
chercher.

\begin{center}
\begin{tabular}{c}
\hline
\\
\texttt{annotation/} \; et le fichier \texttt{umlg.rules} \quad ce que l'utilisateur écrit \\
$\downarrow$ \\
\texttt{extraction/} \quad lecture du code compilé, par réflexion \\
$\downarrow$ \\
\texttt{model/} \quad le diagramme, décrit sans savoir comment il sera dessiné \\
$\downarrow$ \\
\texttt{rendering/} \quad traduction en code PlantUML, puis en image \\
\\
\hline
\end{tabular}
\end{center}

\noindent Un cinquième dossier, \texttt{processing/}, est \emph{hors} de cette chaîne : il
s'exécute à l'intérieur du compilateur, et non à la génération. Il est décrit à part.

\subsection{Les trois endroits où quelque chose se décide}

Cette question revient sans cesse : \emph{où écrit-on ce réglage ?} La réponse tient en une
phrase, et elle explique la présence du fichier de règles à côté des annotations.

\begin{itemize}
  \item Si la décision \textbf{désigne un élément par son nom} — cette classe-ci s'appelle ainsi,
        cet attribut-là est un lien — c'est une \textbf{annotation}.
  \item Si elle vaut pour \textbf{tout le projet, ou pour une vue}, c'est une règle du fichier
        \texttt{umlg.rules}.
  \item Si elle ne dit \textbf{rien du diagramme} — son habillage, le sort de la génération
        précédente — c'est une \textbf{option d'appel} du générateur.
\end{itemize}

\noindent D'où une règle de priorité sans exception : \textbf{l'annotation l'emporte toujours sur
la règle}. Le cas particulier, écrit sur l'élément, bat le réglage qui vaut partout.

\subsection{Pourquoi séparer \texttt{model} de \texttt{rendering} ?}

C'est la séparation la plus importante, et la moins évidente. On pourrait croire qu'un modèle
intermédiaire est une complication inutile : pourquoi ne pas écrire directement le code
PlantUML pendant qu'on lit les annotations ?

Parce que les deux étapes n'ont pas les mêmes questions à trancher. L'extraction se demande
\emph{« que dit ce code ? »} ; le rendu se demande \emph{« comment dessiner cela sans casser la
syntaxe de PlantUML ? »}. Mélangées, ces deux questions se contaminent : on se met à refuser un
nom de classe parfaitement légitime en Java — \texttt{"Compte (bancaire)"} — au motif qu'il
gênerait le moteur de rendu. Le défaut serait alors placé au mauvais endroit, et l'utilisateur
paierait pour une contrainte qui ne le regarde pas.

Séparés, chacun fait son travail : l'extraction accepte tout texte qui a un sens, et le rendu
l'\emph{encode} au moment de l'écrire, en fonction de l'endroit où il atterrit. C'est le même
raisonnement qu'entre « filtrer les apostrophes » et « utiliser une requête préparée ».

Bénéfice secondaire, mais réel : le jour où un autre moteur est visé (Mermaid, Graphviz), seul
\texttt{rendering/} est à remplacer.

\subsection{Les trois règles qui reviennent partout}

Une fois ces trois règles comprises, la plupart des décisions du code s'expliquent d'elles-mêmes.

\paragraph{1. Les gardes appartiennent au modèle, le contexte appartient à l'extraction.}
Une règle du type « une multiplicité s'écrit \texttt{0..*} » est vérifiée dans \texttt{model/},
parce que le modèle doit rester sain quelle que soit la façon dont on le construit. Mais le
modèle ne connaît pas votre code : il peut seulement dire \emph{« "0..x" n'est pas une
multiplicité valide »}. Sur un projet de quarante classes, ce message ne mène nulle part.
L'extraction, elle, sait \emph{où} : elle rattrape l'erreur et y ajoute
\texttt{com.banque.Compte.solde}.

\paragraph{2. La sûreté syntaxique s'obtient à la sortie, jamais à l'entrée.}
Aucun caractère n'est interdit dans un nom, un rôle ou une étiquette. Ce sont des textes
destinés à être lus par un humain. C'est \texttt{PlantUmlEscaper} qui les rend inoffensifs au
moment de les écrire. Seul ce dont le vocabulaire est \emph{fermé} — les multiplicités, les
couleurs — est vérifié par liste blanche.

\paragraph{3. L'échec est franc, parce que PlantUML ne l'est pas.}
Face à un nom de classe inconnu, PlantUML n'échoue pas : il invente une boîte vide portant ce
nom. Face à une couleur inconnue, il produit une image d'erreur parfaitement valide. Dans les
deux cas, le résultat est un fichier de taille normale, indiscernable d'un vrai diagramme.
C'est pourquoi la bibliothèque vérifie elle-même, en amont, et refuse bruyamment.

\section{Le dossier racine : \texttt{umlg/}}

Peu de fichiers, et c'est voulu : c'est la porte d'entrée, et tout ce qui s'y trouve est public.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{UMLGenerator} &
La façade publique. C'est la seule classe qu'un utilisateur de la bibliothèque a besoin de
connaître. Elle enchaîne les deux grandes étapes — scanner, puis écrire — et rien d'autre.
Elle se construit par un \emph{builder} (\texttt{sourceDirectory}, puis \texttt{outputFile} pour
un seul dessin ou \texttt{outputDirectory} pour toutes les vues), ce qui permet de vérifier tôt
que le dossier existe et que le format demandé est bien du \texttt{.png} ou du \texttt{.svg}.
C'est aussi là que se posent les options d'appel — \texttt{style}, \texttt{keepPrevious} —, celles
qui ne disent rien du diagramme. Contient un \texttt{main}, pour la ligne de commande. \\
\addlinespace
\texttt{UmlStyle} &
L'habillage : couleurs, épaisseur des traits, police. Ne change jamais ce que le diagramme
\emph{dit} — les mêmes boîtes, les mêmes traits — seulement son apparence. \\
\addlinespace
\texttt{RapportDeGeneration} &
Ce que la génération a fait : combien de diagrammes, où, combien de classes dessinées et
ignorées. La bibliothèque le \emph{rend} au lieu de l'afficher : choisir le canal n'appartient
pas à une bibliothèque, mais à celui qui l'appelle. \\
\addlinespace
\texttt{Avertissements} &
Où partent les avertissements, pour la même raison. Le plugin Maven les dirige vers son
\emph{log}, la ligne de commande vers la sortie d'erreur. \\
\bottomrule
\end{longtable}

\section{\texttt{annotation/} — le vocabulaire offert à l'utilisateur}

Ce dossier est, avec \texttt{UMLGenerator}, la \textbf{surface publique} de la bibliothèque :
tout le reste est de la mécanique interne. Les fichiers y sont très courts, car une annotation
Java ne fait rien — elle se contente de \emph{déclarer}. Aucune validation n'y a lieu : le
compilateur garantit les types, le modèle garantit le reste.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{UMLClass} &
Le déclencheur. Une classe sans cette annotation n'existe pas pour la bibliothèque. Porte les
quatre réglages de la boîte : \texttt{name} (l'étiquette affichée), \texttt{color},
\texttt{stereotype}, et \texttt{strategy} (le seuil de visibilité, voir ci-dessous). \\
\addlinespace
\texttt{UMLVisibility} &
L'énumération des seuils : \texttt{NONE} (aucun membre affiché, valeur par défaut),
\texttt{PUBLIC}, \texttt{PROTECTED}, \texttt{PACKAGE}, \texttt{PRIVATE} (tout). Répond à la
question « jusqu'à quel niveau de visibilité Java les membres apparaissent-ils ? ». \\
\addlinespace
\texttt{UMLInclude} \newline \texttt{UMLExclude} &
Les deux dérogations, posées sur un attribut ou une méthode. Elles l'emportent toujours sur la
stratégie : \texttt{@UMLInclude} fait apparaître ce qu'elle masquerait, \texttt{@UMLExclude}
masque ce qu'elle afficherait. En cas de conflit, \texttt{@UMLExclude} gagne. \\
\addlinespace
\texttt{UMLAssociation} &
Posée sur un \emph{attribut}, elle le transforme en trait entre deux boîtes. Tous ses
paramètres sont facultatifs : cardinalités, rôles, étiquette, sens du trait, et
\texttt{target} pour désigner explicitement la classe visée quand elle ne peut pas se déduire. \\
\addlinespace
\texttt{UMLRelationType} &
La sémantique du trait : \texttt{ASSOCIATION} (lien simple), \texttt{AGGREGATION} (losange
creux), \texttt{COMPOSITION} (losange plein). Le code Java ne distingue pas ces trois cas —
\texttt{private List<Ligne> lignes} peut être l'un ou l'autre — seul le métier tranche. \\
\addlinespace
\texttt{UMLDirection} &
Une contrainte de \emph{placement} : \texttt{UP}, \texttt{DOWN}, \texttt{LEFT}, \texttt{RIGHT},
ou \texttt{NONE}. Ne change rien au sens du diagramme, seulement à sa mise en page. \\
\addlinespace
\texttt{UMLDependency} &
Posée sur la \emph{classe}, elle déclare « celle-ci a besoin de celle-là » sans la détenir.
C'est la seule façon de faire apparaître un lien que le code ne porte pas structurellement :
un service appelé dans le corps d'une méthode n'est pas un attribut, rien ne pourrait en être
déduit. \\
\addlinespace
\texttt{UMLAssociationClass} &
Une classe qui qualifie un lien — ce que Java ne sait pas exprimer autrement que par une classe
intermédiaire. UML la relie au trait par un pointillé. \\
\addlinespace
\texttt{UMLMultiplicity} \newline \texttt{UMLDerived} \newline \texttt{UMLNotation} &
Trois précisions sur une ligne de boîte : combien d'éléments (\texttt{0..*}), si la propriété est
\emph{calculée} plutôt que stockée (la barre oblique d'UML), et sous quelle forme un lien se
dessine — un trait, ou une ligne dans la boîte. \\
\addlinespace
\texttt{UMLNote} \newline \texttt{UMLConstraint} &
Ce qu'on ajoute au dessin sans l'inventer : une bulle de commentaire, et une règle formelle entre
accolades (\texttt{\{ordered\}}). Toutes deux se posent sur une classe comme sur un membre. \\
\addlinespace
\texttt{UMLPackage} &
Le rectangle nommé dans lequel une boîte se range, avec sa couleur. C'est le \emph{seul} moyen de
grouper : ranger désigne des classes par leur nom, donc c'est une annotation, jamais une règle. \\
\addlinespace
\texttt{UMLFlow} &
Le sens dans lequel un dessin se déplie : de haut en bas, ou de gauche à droite. \\
\addlinespace
\texttt{UMLDependencies} \newline \texttt{UMLNotes} \newline \texttt{UMLConstraints} &
Purement techniques, jamais écrites à la main. Java exige un conteneur pour qu'une annotation
puisse être \emph{répétée} sur le même élément. C'est ce qui permet d'écrire plusieurs
\texttt{@UMLDependency} d'affilée. \\
\addlinespace
\texttt{package-info} &
Documentation du paquetage : son statut public, et la marche à suivre pour l'étendre. \\
\bottomrule
\end{longtable}

\section{\texttt{model/} — le diagramme, dit et non dessiné}

Ce dossier décrit le diagramme \emph{sans savoir} qu'il sera rendu par PlantUML. Tous les
fichiers y sont des \texttt{record} Java : des objets immuables, qui vérifient leur cohérence à
la construction et ne peuvent plus changer ensuite. Un modèle qui se laisserait modifier après
coup ne pourrait rien garantir.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{UmlProject} &
L'ensemble des entités du diagramme, et les vues qu'on en tire. Refuse d'être vide : scanner un
projet où personne n'a annoté doit produire une erreur compréhensible, pas une image blanche. \\
\addlinespace
\texttt{UmlView} &
Un sous-ensemble du diagramme, dessiné dans son propre fichier. Un projet réel ne tient pas sur
une image : la vue intégrale sert de plan, et chaque vue détaille un sujet. \\
\addlinespace
\texttt{UmlDiagram} &
Les réglages qui valent pour le dessin d'ensemble : son titre, son sens de lecture, le sort des
compartiments restés vides. \\
\addlinespace
\texttt{UmlEntity} &
Une boîte. Porte deux noms qu'il ne faut surtout pas confondre : \texttt{qualifiedName} est son
\emph{identité} (\texttt{com.banque.Compte}), \texttt{name} son \emph{étiquette} (ce que le
lecteur voit). L'étiquette est libre, donc ni unique ni reliée au code ; c'est pourquoi les
liens désignent toujours leur cible par le nom qualifié, qui, lui, ne ment pas. Contient aussi
ses membres et \emph{tous} ses liens sortants. \\
\addlinespace
\texttt{UmlField} \newline \texttt{UmlMethod} &
Une ligne de la boîte : nom, type, symbole de visibilité (\texttt{+ - \# \textasciitilde}),
caractère statique, et pour la méthode la liste des types de paramètres. \\
\addlinespace
\texttt{UmlRelation} &
\textbf{La pièce centrale pour la suite du projet.} C'est une interface \emph{scellée} : elle
énumère elle-même les natures de liens qui existent. Grâce à elle, une entité n'a qu'\emph{une
seule} liste de liens, toutes natures confondues. Voir la section~\ref{sec:croissance}, qui
explique ce que cela change concrètement. \\
\addlinespace
\texttt{UmlAssociation} &
Un lien \emph{structurel} : une extrémité détient l'autre. Porte les cardinalités, les rôles,
le qualificatif, l'étiquette et le sens. Vérifie ici que les multiplicités sont bien formées
\emph{et} cohérentes : \texttt{5..2} est syntaxiquement irréprochable et vide de sens, PlantUML
l'afficherait sans broncher. \\
\addlinespace
\texttt{UmlDependency} &
Un lien d'\emph{usage} : la source a besoin de la cible, sans la détenir. D'où l'absence de
cardinalité et de rôle — il n'y a pas d'extrémité à décrire, seulement un usage à signaler. \\
\addlinespace
\texttt{UmlInheritance} \newline \texttt{UmlAssociationClass} \newline \texttt{UmlLayout} &
Les trois autres natures de liens : l'héritage (lu dans \texttt{extends} et \texttt{implements},
sans rien annoter), le pointillé qui rattache une classe d'association à son trait, et le lien
\emph{invisible} qui ne sert qu'à placer les boîtes que rien ne relie. \\
\addlinespace
\texttt{UmlNote} \newline \texttt{UmlPackage} \newline \texttt{UmlParameter} &
Les petites pièces : une bulle de commentaire, un rectangle de regroupement, un paramètre de
méthode. \\
\addlinespace
\texttt{package-info} &
Documentation du paquetage : où sont les gardes, et pourquoi tout y est immuable. \\
\bottomrule
\end{longtable}

\paragraph{Une remarque sur l'absence de « source » dans les liens.}
Ni \texttt{UmlAssociation} ni \texttt{UmlDependency} ne mentionnent la classe d'où part le
trait. Ce n'est pas un oubli : la source \emph{est} l'entité dans la liste de laquelle le lien
figure. Un lien ne peut donc être ni orphelin, ni attribué à une source autre que celle qui le
déclare — deux erreurs qu'il serait autrement possible de commettre.

\section{\texttt{extraction/} — la lecture du code}

Ce dossier lit les fichiers \texttt{.class} compilés et les traduit en modèle, par
\emph{réflexion} (l'API Java qui permet d'interroger une classe à l'exécution).

C'est le dossier le plus fourni, et il est découpé en \textbf{trois sous-dossiers}, parce que
chacun de ces sujets grossit de son côté : ce qui remplit une boîte (\texttt{member/}), ce qui
tend un trait entre deux boîtes (\texttt{relation/}), et ce que le projet a réglé une fois pour
toutes (\texttt{rules/}). Réunis, ils se gênaient.

Seuls \texttt{ProjectScanner} et \texttt{EntityExtractor} sont publics ; presque tout le reste est
volontairement invisible hors du paquetage. C'est là que se lit le contrat : ce qui n'est pas
public n'a pas à rester stable.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{ProjectScanner} &
Parcourt un dossier de \texttt{.class}, les charge, et retient ceux qui portent
\texttt{@UMLClass}. C'est aussi lui qui \emph{signale} ce qui vaut d'être vu sans arrêter le
dessin : boîtes vides faute de stratégie déclarée, compilation sans \texttt{-parameters}, règles
restées lettre morte. \\
\addlinespace
\texttt{EntityExtractor} &
Le chef d'orchestre, et rien d'autre. Il valide l'en-tête, demande les membres, puis parcourt son
\textbf{catalogue d'extracteurs de liens}. Il ne connaît aucune nature de lien en particulier —
seulement leur liste. \\
\addlinespace
\texttt{ClassHeaderValidator} &
Les gardes sur ce que \texttt{@UMLClass} déclare : \texttt{name}, \texttt{stereotype},
\texttt{color}. Illustre la règle n\textsuperscript{o}2 : le nom n'a qu'une contrainte
(désigner quelque chose), la couleur est vérifiée par liste blanche. \\
\addlinespace
\texttt{ConstructeurDeVues} &
Taille le projet en vues : l'intégrale, celles que le fichier déclare, celles qu'il fait calculer
(une par paquetage). Les vues sont découpées ici et non au rendu, car elles dépendent des règles
du projet, que seule l'extraction a lues. \\
\addlinespace
\texttt{TypeAffiche} &
Écrit un type tel qu'il paraîtra dans une boîte, paramètres de type compris — et c'est ici que
les renommages du fichier de règles (\texttt{ImmutableList} affiché « List ») s'appliquent. \\
\addlinespace
\texttt{MembresOrdonnes} \newline \texttt{OrdreDuFichierClasse} &
L'ordre des membres dans une boîte : l'alphabet par défaut, ou l'ordre du code si le projet le
demande. La réflexion ne promet aucun ordre ; le second relit donc le fichier \texttt{.class}
pour retrouver celui de la déclaration. \\
\addlinespace
\texttt{PackageExtractor} \newline \texttt{NoteExtractor} \newline \texttt{ConstraintExtractor} &
Les trois lectures secondaires : le rectangle de regroupement, les bulles de commentaire, les
règles formelles entre accolades. \\
\addlinespace
\texttt{package-info} &
Documentation du paquetage : statut de chaque classe, et le point d'extension. \\
\bottomrule
\end{longtable}

\subsection{\texttt{extraction/member/} — ce qui remplit une boîte}

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{MemberExtractor} &
Parcourt attributs et méthodes, et traduit ceux qui sont retenus. Écarte au passage un attribut
promu en lien : en UML, une propriété se note dans la boîte \emph{ou} comme un trait, jamais les
deux. \\
\addlinespace
\texttt{VisibilityPolicy} &
Répond à « ce membre paraît-il ? », et « sous quel symbole ? ». Applique d'abord les
dérogations, puis le seuil. Écrit avec un \texttt{switch} exhaustif : ajouter une valeur à
\texttt{UMLVisibility} sans dire ce qu'elle retient devient une erreur de compilation. \\
\addlinespace
\texttt{NoiseFilter} &
\emph{Reconnaît} la plomberie — getters, setters, \texttt{toString}, accesseurs de
\texttt{record}, méthodes que \texttt{javac} ajoute aux \texttt{enum} — sans jamais décider de la
masquer : c'est le fichier de règles qui le demande, famille par famille. Détail crucial : la
détection exige la convention JavaBean \emph{complète} (préfixe suivi d'une majuscule, arité,
type de retour). Un simple test de préfixe faisait disparaître silencieusement
\texttt{setup()}, \texttt{issue()}, \texttt{getaway()}, \texttt{isoler()} — de vraies méthodes
métier. \\
\bottomrule
\end{longtable}

\subsection{\texttt{extraction/relation/} — ce qui tend un trait}

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{RelationExtractor} &
\textbf{Le point d'extension.} Une interface : « voici une classe, donne-moi les liens que tu
sais y lire ». Une implémentation par nature de lien. \\
\addlinespace
\texttt{AssociationExtractor} \newline \texttt{DependencyExtractor} \newline
\texttt{InheritanceExtractor} \newline \texttt{AssociationClassExtractor} &
Les quatre implémentations. Notez qu'un lien n'est \emph{pas} soumis à la stratégie de
visibilité : une composition ne disparaît pas parce que le champ qui la porte est privé — c'est
même le cas le plus courant. L'héritage, lui, ne s'annote pas : il se lit dans \texttt{extends}
et \texttt{implements}. \\
\addlinespace
\texttt{TargetResolver} \newline \texttt{CibleDeduite} &
La question la plus difficile du dossier : \emph{vers quoi pointe ce lien quand l'annotation ne
le dit pas ?} Savent déduire l'élément d'un tableau, le contenu d'une collection ou d'un
\texttt{Optional}, la valeur d'une \texttt{Map}. Refusent franchement quand le code ne dit rien
(\texttt{List} brute, \texttt{List<T>}) : deviner produirait un lien faux, qui se lit exactement
comme un lien vrai. \\
\addlinespace
\texttt{Emplacement} &
Une seule méthode, et pourtant un fichier à elle : elle produit le « où » des messages d'erreur
(\texttt{com.banque.Compte.solde}). Chaque extracteur à venir doit désigner la déclaration
fautive de la même façon, et non chacun à la sienne. \\
\bottomrule
\end{longtable}

\subsection{\texttt{extraction/rules/} — ce que le projet règle une fois pour toutes}

Une annotation dit une chose sur un élément. Écrire « affiche \texttt{ImmutableList} comme
\texttt{List} » sur chacun des deux cents attributs d'un projet est un travail que personne ne
fait, et que personne ne tient à jour. D'où un fichier, \texttt{umlg.rules}, posé à la racine du
répertoire analysé — facultatif, et lu une seule fois avant la première classe.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{LecteurDeRegles} &
Lit le fichier ligne à ligne. Une règle commence par un mot-clé qui dit sa nature — il y en a
onze — et c'est lui qui décide comment lire le reste. Le vocabulaire est \textbf{fermé} : un mot
inconnu \emph{arrête} la génération, plutôt que d'appliquer en silence des règles dont une partie
serait ignorée. Chaque refus nomme le fichier et le numéro de ligne : il n'y a pas de compilateur
pour relire ce que l'utilisateur écrit ici. \\
\addlinespace
\texttt{Regles} &
Le résultat de cette lecture, interrogé par tout le reste de l'extraction. Retient au passage
quelles lignes ont \emph{servi} : une règle qui ne vise plus rien — une classe renommée, une
faute de frappe — est un no-op parfait, que rien d'autre ne signalerait. \\
\addlinespace
\texttt{Motif} \newline \texttt{Bruit} &
Les deux façons de désigner des membres : un motif de noms (\texttt{get*}, \texttt{*Cache}), et
les quatre familles reconnues à leur \emph{forme}. Un motif ne peut pas contenir de point :
désigner un membre par son nom est le travail d'une annotation. \\
\addlinespace
\texttt{DefinitionDeVue} \newline \texttt{Selecteur} &
Ce qu'une vue retient, et comment on le désigne : une classe, un paquetage entier, ou le
voisinage immédiat d'une classe. \\
\bottomrule
\end{longtable}

\section{\texttt{rendering/} — le dessin}

Ce dossier est le seul à connaître la syntaxe de PlantUML. Seul \texttt{PlantUmlWriter} est
public. Il se découpe en deux sous-dossiers : \texttt{element/} écrit \emph{un} morceau du dessin
— une boîte, un trait —, et \texttt{syntax/} règle ce que le moteur exige de tous.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{PlantUmlWriter} &
Le chef d'orchestre du rendu : construit le document, puis demande à PlantUML de produire le
\texttt{.svg} ou le \texttt{.png}. Applique la règle des \textbf{deux passes} — toutes les
boîtes d'abord, tous les traits ensuite — car un trait nomme ses extrémités par un identifiant
qui n'existe qu'une fois la boîte déclarée. \\
\addlinespace
\texttt{PlantUmlSyntaxBuilder} &
Assemble le document. Ne connaît plus de la syntaxe que l'\emph{ordre} des morceaux, ce
qu'aucun de ses collaborateurs ne peut savoir seul : les classes avant les liens, et le bloc de
style en tête bien qu'il ne soit calculable qu'à la fin. \\
\addlinespace
\texttt{AssociationsReciproques} &
Deux attributs qui se font face ne sont qu'\emph{une} association. Sans cette passe, le même lien
serait dessiné deux fois, une fois depuis chaque bout. \\
\addlinespace
\texttt{Proportions} &
Mesure l'image produite et signale celle qu'on ne pourra pas lire — un ruban de douze contre un.
C'est le seul contrôle qui exige que le dessin existe déjà. \\
\addlinespace
\texttt{package-info} &
Documentation du paquetage, dont l'asymétrie « ouvert à l'extraction, fermé au rendu ». \\
\bottomrule
\end{longtable}

\subsection{\texttt{rendering/element/} — un morceau du dessin}

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{ClassBoxRenderer} &
Écrit une boîte : son en-tête, ses attributs, le filet séparateur, ses méthodes. L'ordre des
morceaux de l'en-tête n'est pas libre — le moteur accepte \texttt{[[lien]] \#couleur} et refuse
l'inverse, sans le dire. \\
\addlinespace
\texttt{RelationRenderer} \newline \texttt{Extremite} &
Écrivent un trait, quelle que soit sa nature, par un \texttt{switch} sur \texttt{UmlRelation}, et
l'étiquette posée à chacun de ses bouts (« achats 0..* »). Retiennent au passage la largeur de la
plus large : c'est ici, et nulle part ailleurs, que le diagramme apprend de quel espace il aura
besoin entre ses boîtes. \\
\addlinespace
\texttt{NoteRenderer} \newline \texttt{PackageRenderer} &
La bulle de commentaire, et le rectangle qui entoure un groupe de boîtes. \\
\bottomrule
\end{longtable}

\subsection{\texttt{rendering/syntax/} — ce que le moteur exige}

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{AliasRegistry} &
L'annuaire du document : à chaque classe, l'identifiant court par lequel PlantUML la désignera.
Traite deux pièges que PlantUML ne signale pas : un nom sans aucun caractère alphanumérique
ASCII (un nom en idéogrammes, ou «~...~») donnerait un identifiant vide, et deux noms distincts
peuvent se réduire au même
(«~Mon.Client~» et «~MonClient~»), auquel cas PlantUML fusionnerait silencieusement les deux
classes. \\
\addlinespace
\texttt{PlantUmlEscaper} &
L'encodage de sortie (règle n\textsuperscript{o}2). Neutralise ce qui casserait la syntaxe ou
permettrait une injection. Ce n'est pas cosmétique : les étiquettes PlantUML acceptent des
balises, dont \texttt{<img:/chemin>}, qui fait lire un fichier local au moteur de rendu. \\
\addlinespace
\texttt{ColorCodec} &
Vérifie qu'une couleur existe vraiment, en interrogeant le catalogue de PlantUML — la seule
autorité en la matière, et la raison pour laquelle cette vérification n'est pas à l'extraction. \\
\addlinespace
\texttt{PlantUmlLayout} &
Tout ce qui ne change rien à ce que le diagramme \emph{dit}, et tout à la facilité avec
laquelle on le \emph{lit} : police, couleurs, coins arrondis, et surtout l'espacement entre
boîtes, calculé d'après la plus longue étiquette — c'est ce réglage qui décide, à lui seul, si
les textes se chevauchent. \\
\addlinespace
\texttt{package-info} &
Documentation du paquetage : ce qui relève du moteur, et ce qui n'en relève pas. \\
\bottomrule
\end{longtable}

\section{\texttt{processing/} — la vérification à la compilation}

Ce dossier est le seul à ne pas participer à la chaîne. Il contient un \textbf{processeur
d'annotations} : du code qui s'exécute \emph{à l'intérieur de \texttt{javac}}. Il ne produit
rien ; il lit les annotations et refuse la compilation quand elles sont fautives.

Pourquoi le faire deux fois, puisque la génération vérifie déjà ? À cause du \textbf{moment}.
Une annotation contradictoire découverte à la génération se paie d'un aller-retour : on lance
l'outil, on lit un message, on retourne au code. Découverte à la compilation, elle est signalée
comme n'importe quelle erreur Java — soulignée dans l'éditeur, à la ligne près, avant même
d'avoir enregistré. C'est la différence entre un correcteur orthographique et une relecture.

\begin{longtable}{L{4.2cm} L{10cm}}
\toprule
\textbf{Fichier} & \textbf{Rôle} \\
\midrule
\endhead
\texttt{UmlgProcessor} &
Le point d'entrée, déclaré à \texttt{javac}. Il ne vérifie rien lui-même : il distribue chaque
élément annoté aux vérificateurs. \\
\addlinespace
Les \texttt{Verificateur*} &
Un par sujet — les classes, les membres, les associations, les multiplicités, les contraintes,
les notes… Chacun connaît une famille de fautes et le message qui l'explique. \\
\addlinespace
\texttt{Rapporteur} &
La distinction qui structure tout le dossier : une \textbf{erreur} arrête la compilation, un
\textbf{avertissement} la laisse passer. La frontière est une règle, pas une nuance de ton :
est une erreur ce qui rendrait le diagramme \emph{faux}, un avertissement ce qui le rendrait
seulement \emph{différent} de ce qu'on croyait demander. \\
\addlinespace
\texttt{Strategie} &
Le seul point délicat. Le défaut de \texttt{@UMLClass} renvoie au fichier \texttt{umlg.rules} —
que \texttt{javac} ne sait pas trouver, puisqu'il compile des sources et ignore ce que la
construction fera du résultat. Sans lui, tous les messages du genre « ce membre n'est pas
affiché » deviennent indécidables, et le processeur \emph{se tait} : un avertissement qui se
trompe coûte plus cher que celui qui manque un cas, puisqu'il apprend à ne plus les lire. \\
\bottomrule
\end{longtable}

\section{Ajouter une nature de lien : le mode d'emploi}
\label{sec:croissance}

C'est le scénario pour lequel l'architecture a été réorganisée. Supposons que vous vouliez
ajouter \texttt{@UMLInheritance} (l'héritage). Voici la liste complète de ce qu'il faut faire :

\begin{enumerate}
  \item \textbf{Déclarer l'annotation} : un nouveau fichier dans \texttt{annotation/}.
  \item \textbf{Déclarer le lien dans le modèle} : un nouveau \texttt{record} dans
        \texttt{model/}, qui implémente \texttt{UmlRelation}, et une mention dans la clause
        \texttt{permits} de celle-ci.
  \item \textbf{Écrire la lecture} : une classe dans \texttt{extraction/relation/} qui implémente
        \texttt{RelationExtractor}, plus \emph{une ligne} dans le catalogue
        \texttt{EXTRACTEURS} d'\texttt{EntityExtractor}.
  \item \textbf{Écrire le dessin} : les \texttt{case} manquants dans \texttt{RelationRenderer} —
        le compilateur dit lesquels.
\end{enumerate}

\paragraph{Ce qui ne bouge pas.} Ni \texttt{UmlEntity}, ni le corps d'\texttt{EntityExtractor},
ni \texttt{PlantUmlSyntaxBuilder}, ni \texttt{PlantUmlWriter}. Auparavant, \texttt{UmlEntity}
devait être modifié en cinq endroits, et \texttt{PlantUmlSyntaxBuilder} en deux.

\paragraph{Ce que le compilateur garantit.} Si vous oubliez l'étape 4, le projet
\textbf{ne compile pas}. Le compilateur pointe précisément les deux \texttt{switch} à
compléter. C'est toute la raison d'être de l'interface \emph{scellée} : auparavant, un lien non
dessiné disparaissait simplement du diagramme, sans erreur, sans avertissement — le dessin
paraissait juste un peu plus simple qu'il n'aurait dû.

\paragraph{Pourquoi ouvert d'un côté et fermé de l'autre ?} L'asymétrie est délibérée, et
repose sur ce que coûte l'oubli. Oublier un extracteur ne produit \emph{rien} : la liste est
explicite et se relit. Oublier un dessin produit un diagramme \emph{plausible} mais amputé
d'une famille entière de traits — l'erreur la plus coûteuse, puisque rien ne la signale.

\section{\texttt{src/test/} — les tests, en miroir}

Les tests suivent exactement le découpage des sources : à chaque classe qui porte une
responsabilité correspond un fichier de tests qui la vérifie, dans le même sous-dossier. Cela
vaut mode d'emploi : pour comprendre ce que fait \texttt{NoiseFilter}, \texttt{NoiseFilterTest}
est souvent plus instructif que le code lui-même, parce qu'il montre les cas limites qui ont
motivé chaque ligne. Le fichier à ouvrir se déduit donc du nom de la classe, et il n'y a pas de
catalogue à tenir à jour ici.

Deux familles échappent à ce miroir, et c'est délibéré.

\paragraph{Les tests nommés d'après une fonctionnalité.} \texttt{PlantUmlEscapeTest},
\texttt{PlantUmlLisibiliteTest}, \texttt{AffichageDesMembresTest} portent le nom de ce qui est
\emph{rendu}, non de la classe qui l'implémente. C'est un axe de découpage tout aussi légitime,
et il a un avantage propre : ces tests vérifient le document produit dans son ensemble, ce
qu'aucun test d'une classe isolée ne pourrait faire.

\paragraph{Les tests de bout en bout.} \texttt{DuCodeCompileAuPumlTest} écrit un petit projet,
le \emph{compile pour de bon}, pose un fichier de règles à côté et vérifie les \texttt{.puml}
livrés. C'est le seul niveau où l'on voit la chaîne entière, et donc le seul où se voient les
défauts qui vivent \emph{entre} deux étapes — chacune irréprochable de son côté.
